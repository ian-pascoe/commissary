# How self-hostable products with a paid cloud license their code

Research for ticket #106 (map #101). Researched 2026-10-15 against each project's own LICENSE files, license-author sites and first-party blog posts. This is not legal advice; the decision is made in a later grilling ticket.

## Answer

1. **Comparable products fall into four patterns.** (a) Permissive core plus a proprietary `ee/` directory ("open core"): LiteLLM, Langfuse, PostHog. (b) Fully permissive: Supabase (Apache-2.0). (c) Source-available with a competing-use ban: Sentry (FSL), n8n (Sustainable Use License), Dify (modified Apache-2.0 that bans multi-tenant hosting). (d) Copyleft plus proprietary enterprise parts: Windmill (AGPLv3 core, Apache-2.0 clients, proprietary EE code). Cal.com was MIT with an `ee` split and went closed source on 2026-04-14, keeping an MIT community fork, Cal.diy.
2. **Only the permissive-core pattern leaves the "hosted competitor" door open.** Sentry, n8n, Dify and Windmill each wrote hosted-resale protection into their license. Sentry says so explicitly ("protections from other companies selling our work") and picked FSL for it.
3. **What happened as a result.** Companies that relicensed *existing* open-source code to non-open terms (HashiCorp, Redis, Elastic) drew forks (OpenTofu, Valkey, OpenSearch). Two of them later added an OSI license back (Elastic AGPL Aug 2024; Redis AGPLv3 May 2025). Sentry, n8n and Dify chose a restrictive license at or near the point they grew a cloud business, and I found no comparable fork episode for them. That is the absence of evidence in my search, not proof. Langfuse moved the other way: in June 2025 it MIT-licensed all product features that had been gated in `ee/`.
4. **Commissary's own code need not match upstream's license.** CLIProxyAPI is MIT. MIT requires only that "the above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software". It expressly permits sublicensing. So Commissary may put its own code under any license (proprietary, AGPL, FSL, ...) provided the upstream copyright and MIT text ship with the copied or derived parts. The MIT-licensed upstream portions stay MIT for everyone; Commissary cannot re-license *those* exclusively.
5. **Repo state today.** `LICENSE` is MIT with only the upstream copyright lines (Luis Pater; Router-For.ME); README says "MIT, including the original CLIProxyAPI copyright notice". There is no Commissary copyright line yet. 414 files under `src/` reference Go paths (`internal/...`, `sdk/...`), so the port is derivative in many places and the notice must be kept wherever that code is.
6. **Open trade-off for the grilling ticket**: a single-license repo (simple, matches self-host story) versus split licensing (MIT/Apache core, separate license for hosted-only areas such as Browser/Agents). Contributor terms (CLA or none) decide whether the owner can later relicense; see "Relicensing power".

## License families (owner sources)

- **FSL** ([fsl.software](https://fsl.software/), license text in Sentry's LICENSE.md): all features available; no *Competing Use* (a commercial product that substitutes for the software or offers same/substantially similar functionality); internal use, education, research and professional services allowed; converts to Apache-2.0 or MIT two years after each release. The authors say it is tuned for SaaS companies, not for charging for on-prem use or library embedding, and they position it as "Fair Source", not Open Source.
- **BSL**: source-available, flexible additional-use grant, converts after a set date (default 4 years per Sentry's FSL post); "formally not an open-source license" per Sentry's 2019 post.
- **AGPLv3**: OSI-approved; §13 network-use clause. FSL's FAQ argues AGPL is "outside of policy" at some organizations (FSL is an interested party).
- **Open core by directory** (LiteLLM, PostHog, Langfuse, n8n `.ee.`): proprietary files in labelled paths, usable in production only with a subscription.

## Consequences observed

- HashiCorp MPL-2.0 → BSL (2023-08-10, [HashiCorp](https://www.hashicorp.com/en/blog/hashicorp-adopts-business-source-license)). Linux Foundation launched OpenTofu on 2023-09-20 as the response ([LF](https://www.linuxfoundation.org/press/announcing-opentofu)).
- Redis moved to SSPL/RSAL in March 2024; Valkey (Linux Foundation, based on Redis 7.2.4, BSD-3) appeared ([LF 2024-04-16](https://www.linuxfoundation.org/press/valkey-community-announces-release-candidate-amid-growing-support-for-open-source-data-store)). Redis added AGPLv3 from Redis 8 on 2025-05-01 and says the change "hurt our relationship with the Redis community" ([Redis](https://redis.io/blog/agplv3.md)).
- Elastic added AGPL as an option on 2024-08-29 to make Elasticsearch/Kibana "officially considered open source" again ([Elastic IR](https://ir.elastic.co/News--Events/news/news-details/2024/Elastic-Announces-Open-Source-License-for-Elasticsearch-and-Kibana-Source-Code/default.aspx)). OpenSearch (the fork) I did not source here; only mentioned by a secondary summary.
- Pattern: forks follow when a license *tightens* on code the community already depended on and the project is foundation-adoptable. A new project that starts with the restrictive license has no such "taking away" event. This is my inference from the cases above, not a stated finding by any source.
- Cal.com: closed-sourced 2026-04-14; community fork Cal.diy is MIT. Too recent to assess outcome.

## What CLIProxyAPI's MIT license requires

Source: upstream [LICENSE](https://raw.githubusercontent.com/router-for-me/CLIProxyAPI/main/LICENSE) (copyright "2025-2005.9 Luis Pater", "2025.9-present Router-For.ME" – the first range looks like a typo for 2005.9 upstream, quoted as-is) and the MIT text ([choosealicense.com](https://choosealicense.com/licenses/mit/): "conditions only requiring preservation of copyright and license notices. Licensed works, modifications, and larger works may be distributed under different terms and without source code.").

- Must: include the upstream copyright notice and MIT permission notice in all copies or substantial portions (source or binaries, per the text's "copies").
- May: modify, commercialise, sublicense, sell, run as a hosted service, and license the *new* code under different terms, including proprietary.
- No copyleft, no source-disclosure, no attribution-in-UI requirement, no trademark grant (MIT is silent on trademarks; "CLIProxyAPI" name use not covered by a grant, not researched further).
- The copied/derived portions remain available to everyone under MIT; Commissary's license applies to its own additions. A mixed repo should say which files are which (common practice: root LICENSE + a `NOTICE`/third-party section, as the open-core repos above do with "Portions of this software are licensed as follows").
- Models.dev data used for the catalog (ADR 0020) and npm dependencies have their own licenses; I did not audit them.

## Relicensing power

- Dify's license asks contributors to accept that the producer may tighten or loosen terms; Windmill/n8n/PostHog/LiteLLM hold copyright over `ee/` via company-authored code. The Open {re}Source guide notes a company can relicense contributors' copyleft code only with a CLA ([secondary](https://openresource-dev-git-content-plain-english-0d79da-open-resource.vercel.app/guide/licensing/relicensing)); I did not verify this against a legal primary source.
- MIT/Apache contributions already received under their license cannot be withdrawn, which is why forks can continue from the last open release.

## Gaps and caveats

- I did not read each project's CLA/contributor terms except Dify's (in its LICENSE).
- LiteLLM's and Supabase's pricing/hosting terms and any actual enforcement history not researched.
- Legal effect of FSL/SUL clauses in court is untested in what I found; none of the sources discuss litigation.
- Cal.com's repo naming (cal.com vs cal.diy) is ambiguous as described above.
